# Infrastructure Design -- unit `api-identity` (U1)

**Decisions:** infrastructure plan Q1 A (two secrets per stage, both always mounted; the previous one seeded with a
throwaway random value), Q2 A (the operator sets the values by hand before PR 1's promotion); approved
2026-10-08. Provider: Google Cloud (project `remonta-api-510206`, `australia-southeast1`) and Vercel, as today.

## 1. Logical component to infrastructure mapping

| Logical component (NFR design) | Infrastructure | Stage values |
|---|---|---|
| The api's secret pair | Secret Manager secrets `remonta-api[-staging]-API_TOKEN_SECRET` and `remonta-api[-staging]-API_TOKEN_SECRET_PREVIOUS`, user-managed replication in `australia-southeast1`, label `remonta-stage`, `secretAccessor` for the stage's runtime account only; mounted by the Knative template as env `API_TOKEN_SECRET` / `API_TOKEN_SECRET_PREVIOUS` with `key: latest` | one value per stage, never shared across stages |
| The app's secret | Vercel project `remonta-app`, environment variable `API_TOKEN_SECRET`: Production scope = prod's value, Preview scope = staging's value (CLAUDE.md: previews point at staging) | set by hand in the Vercel dashboard |
| `JwtAuthenticator` | runs inside the existing Cloud Run services (`remonta-api-staging`, `remonta-api`); no new service, no sizing change | -- |
| The token route | runs inside the app's existing Vercel serverless functions; same origin as the admin pages | -- |
| The auth-failure signal | Cloud Logging log-based metric `remonta-api-auth-failed` (project-wide, filtered by service in the policy) + Cloud Monitoring policy `remonta-api auth-failed` (prod only) on the existing email channel "Remonta api alerts" | threshold `> 20` per 300 s |
| Saved queries | documented in `docs/admin/README.md` (Cloud Logging query strings) | -- |

No new compute, storage (beyond the secrets), messaging, networking or environment. The api's CORS already lists
`authorization`; nothing changes on the network path.

## 2. Secret definitions

| Secret (per stage) | Content | Who writes | When |
|---|---|---|---|
| `<service>-API_TOKEN_SECRET` | 32 random bytes, base64 (44 chars), generated by `openssl rand -base64 32` | the operator | before PR 1 is promoted (staging first, prod before the promotion) |
| `<service>-API_TOKEN_SECRET_PREVIOUS` | at bootstrap: a random 32-byte value nobody keeps; during a rotation: the old `API_TOKEN_SECRET`; after the window: a fresh random value again | `bootstrap.sh` (initial), the operator (rotation) | bootstrap; rotations |

Rules: the api refuses to boot unless both are present and at least 32 bytes (config: the current required, the
previous required-when-mounted, which is always); neither value is ever logged, printed by a script, or placed in
the repository, the image or the YAML (the YAML carries only the reference).

## 4. The policy `cloudrun/monitoring/auth-failed.json`

```json
{
  "displayName": "__SERVICE__ auth-failed",
  "documentation": {
    "content": "More than 20 rejected tokens at __SERVICE__ (__STAGE__) in 5 minutes. Each has a warn line {auth:'rejected', reason, entry} with reqId. Reasons: missing, malformed, bad-signature, expired, not-yet-valid, bad-issuer, bad-audience, bad-claims. A burst of bad-signature after a deploy means the app and the api hold different API_TOKEN_SECRET values (check Vercel and Secret Manager, or finish the rotation runbook); a burst of expired from one userId is a stale tab; anything else from many IPs is a scan: the per-IP limits hold, read the reqIds.",
    "mimeType": "text/markdown"
  },
  "combiner": "OR",
  "conditions": [
    {
      "displayName": "rejected tokens in 5 minutes > 20",
      "conditionThreshold": {
        "filter": "resource.type = \"cloud_run_revision\" AND resource.labels.service_name = \"__SERVICE__\" AND metric.type = \"logging.googleapis.com/user/remonta-api-auth-failed\"",
        "aggregations": [{ "alignmentPeriod": "300s", "perSeriesAligner": "ALIGN_SUM", "crossSeriesReducer": "REDUCE_SUM", "groupByFields": ["resource.labels.service_name"] }],
        "comparison": "COMPARISON_GT",
        "thresholdValue": 20,
        "duration": "0s",
        "trigger": { "count": 1 }
      }
    }
  ],
  "notificationChannels": ["__CHANNEL__"],
  "alertStrategy": { "autoClose": "1800s" },
  "severity": "ERROR",
  "userLabels": { "remonta-stage": "__STAGE__", "remonta-service": "api" }
}
```

Applied with `bash infra/cloudrun/apply-alerts.sh prod` after the merge (`--dry-run` shows the diff); staging does
not carry it (`alerts_for staging` unchanged), matching the "minimal" alert set of the stage table.

## 5. Security and least privilege (SECURITY-06, -09, -12)

- Each runtime service account reads only its own stage's eight secrets (`secretAccessor` on each secret, as
  today); the GitHub deploy account gains nothing (it references secrets by name in the YAML; Cloud Run resolves
  them with the runtime account).
- No wildcard grants; no project-level secret roles.
- The Vercel variable is scoped per environment; the Preview scope never holds prod's value.
- Secret Manager keeps version history; old versions are disabled, not destroyed, for one week after a rotation,
  then destroyed (the runbook).
