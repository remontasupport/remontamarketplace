# U2 `tools-app`: business logic model

## Flow W: a worker fills in their tools

```
Services → Cleaning Services → (qualifications/offerings as today) → documents (optional certificate)
  Next ─► ?view=tools                                              (UR-1, UR-7: was "the next service")
          GET /v1/worker/services/tools ─┬ ok ─► MultiSelectField(value = fieldValueOf(entry))   (UR-2, UR-4)
                                         └ fail ─► "We couldn't load your tools." [Retry]          (UR-6)
          worker toggles tags, types "Hose" + Add ─► addOwnTool                                  (UR-3)
          Next ─► PUT .../cleaning-services/tools  bodyOf(value)                                  (UR-5)
                    ├ 200 ─► next service step, or Service Area after the last
                    └ 400/429/5xx/offline ─► stay; message; tags kept; Next again retries
          Previous ─► ?view=documents
```

## Flow A1: an admin filters by tools

```
Filter panel → Tools → toggles "Ladder" (Home and Yard) and "Vacuum cleaner" (Cleaning)
  → pendingFilters.tools = [ladder, vacuum-cleaner] → Apply → URL ?tools=ladder,vacuum-cleaner
  → GET /v1/admin/workers?...&tools=ladder,vacuum-cleaner → the cards (unchanged look)       (UR-8)
```

## Flow A2: an admin opens a worker

```
/admin/contractors/<profileId> → the page as today + GET /v1/admin/workers/<profileId>/services
  → under "Cleaning Services": "Tools: Vacuum cleaner, Mop and bucket · Other: Pressure washer"   (UR-9)
  → read fails: no tools line; the page is unaffected
```

## Flow S: the sign-up

```
"What services can you offer?" → ticks Home and Yard Maintenance
  → (i) "Some jobs require your own tools, so please be ready to bring them."                   (UR-10)
  → unticks it (and Cleaning not ticked) → the note goes
```

## Scenarios

| Scenario | Result |
|---|---|
| Worker types "vacuum CLEANER" + Add on Cleaning | the "Vacuum cleaner" tag is ticked; no own tool added |
| Types a 6th own tool | Add disabled; nothing added |
| Saved `[ladder]`, later "Ladder" renamed in the list | shows the new label, ticked |
| Saved id later removed from the list | not shown; the next Next saves without it |
| Tools read 503 | the retry line; Next goes on without a save |
| Save 429 | "Too many changes at once..." (messageOf); stays on the screen |
| Worker with only Support Worker | no tools screen anywhere |
| Admin with no tools chosen | no `tools` in the URL or the query |

## Properties (PBT, full)

- PU1 `bodyOf(service, fieldValueOf(t)) == t` for any stored `t` with only listed ids (round trip).
- PU2 `bodyOf` always yields ids of that service only, in list order, and own tools that `normaliseOtherTools` leaves
  unchanged, for any value the field can hold (generated by sequences of toggles and `addOwnTool`).
- PU3 `addOwnTool` never produces more than 5 own values, any over 60 characters, or a value equal (ignoring case) to
  another value.
- PU4 `toQuery(filters)` with tools → parsed by the contract's query schema → the same id set (the URL round trip, as
  the existing `query.test.ts` properties do for the other filters).
