# 03 — Data model: what a sign-up reads and writes

Schema: `packages/db/prisma/schema.prisma` (one schema, one migration history). Table names below are the
real Postgres names (`@@map`); `Category` and `Subcategory` have no mapping, so their tables are
literally `"Category"` and `"Subcategory"`. Enums are in [04-enums.md](04-enums.md).

> **Production note (2026-10-01):** the S1 migrations have **not** run on the production database yet.
> Until they do, production has none of the S1 tables (`worker_locations`, `worker_onboarding`,
> `worker_onboarding_transitions`, `registration_photo_uploads`, `outbox_events`, `au_localities`, …) nor
> the three S1 columns on `worker_profiles`. apps/app's auth client omits those columns
> (`apps/app/src/lib/auth-prisma.ts`) so legacy code keeps working. Staging (`rehearse-w1`) has all of it.

## 1. Overview

| Table | Rows per sign-up | Written by | Step |
|---|---|---|---|
| `registration_photo_uploads` | 1 inserted, then claimed | photo upload, then submit | 4.6, 4.7 |
| `users` | 1 | submit | 4.7 |
| `worker_profiles` | 1 | submit | 4.7 |
| `worker_services` | 1 per chosen service | submit | 4.7 |
| `worker_locations` | 1 (`HOME`) | submit | 4.7 |
| `worker_onboarding` | 1 | submit | 4.7 |
| `worker_onboarding_transitions` | 1 | submit | 4.7 |
| `audit_logs` | 1 | submit | 4.7 |
| `outbox_events` | 1 (`WorkerRegistered`) | submit | 4.7 |
| `rate_limit_buckets` | counters | every call | pipeline |

Everything the submit writes is in **one transaction** (R3): all of it or none of it.

An **existing email** writes no account rows: at most one `outbox_events` row
(`RegistrationAttemptOnExistingAccount`, at most one per account per 10 minutes, none in the first
10 minutes after the account was created) and no audit row.

## 2. Tables written by a sign-up

"Value" says where each column's value comes from. Columns a sign-up does not set keep their defaults
(or NULL) and are filled in later by onboarding.

### 2.1 `users`

| Column | Type | Value at sign-up |
|---|---|---|
| `id` | text (cuid) | generated |
| `email` | text, unique | `email`, trimmed and lower-cased |
| `passwordHash` | text | hash of `password` (worker pool hasher) |
| `role` | `UserRole` | `WORKER` |
| `status` | `AccountStatus` | `ACTIVE` (the account works at once) |
| `resetPasswordToken`, `resetPasswordExpires` | | NULL |
| `failedLoginAttempts` | int | 0 (default) |
| `accountLockedUntil`, `lastLoginAt`, `lastLoginIp` | | NULL |
| `createdAt` | timestamp | now (default) |
| `updatedAt` | timestamp | now |

Email look-ups use the index `users_lower_email_idx` on `lower(email)`.

### 2.2 `worker_profiles`

| Column | Type | Value at sign-up |
|---|---|---|
| `id` | text (cuid) | generated |
| `userId` | text, unique | the new `users.id` |
| `firstName`, `lastName` | text | normalised `firstName` / `lastName` |
| `mobile` | text | `mobile` as E.164, `+614XXXXXXXX` |
| `photos` | text | the Blob URL of the claimed photo |
| `location` | text | legacy shape: `"Parramatta, NSW 2150"` |
| `city` | text | the locality's suburb |
| `state` | text | the locality's state |
| `postalCode` | text | the locality's postcode |
| `latitude`, `longitude` | float | the locality's centroid |
| `languages` | text[] | `[]` |
| `profileCompleted` | bool | false |
| `isPublished` | bool | false |
| `verificationStatus` | text (not a DB enum) | `NOT_STARTED` — see [04 §10](04-enums.md#10-worker_profilesverificationstatus-text-not-a-db-enum) |
| `consentProfileShareAt` | timestamp | now (S1 column) |
| `consentWordingVersion` | text | `worker-profile-share-v1` (S1 column) |
| `zohoLeadId` | text | `zohoLeadId` if valid, else NULL (S1 column) |
| `createdAt`, `updatedAt` | timestamp | now |
| everything else (`middleName`, `dateOfBirth`, `gender`, `abn`, `setupProgress`, …) | | NULL / default — onboarding fills them |

The legacy location columns (`location`, `city`, `state`, `postalCode`, `latitude`, `longitude`) are
written in exactly the shape apps/app writes, so every existing reader (search included) keeps working.

### 2.3 `worker_services` — one row per chosen service

| Column | Type | Value |
|---|---|---|
| `id` | text (uuid) | generated by the database |
| `workerProfileId` | text | the new profile |
| `categoryId` | text | a `services` id |
| `categoryName` | text | that category's name (copied) |
| `subcategoryIds` | text[] | the chosen `supportWorkerCategories` that belong to this category |
| `subcategoryNames` | text[] | their names (copied) |
| `metadata` | json | NULL |

Unique on (`workerProfileId`, `categoryId`). Rows are in the order the worker chose.

### 2.4 `worker_locations` — the HOME location

| Column | Type | Value |
|---|---|---|
| `id` | text | random uuid |
| `workerProfileId` | text | the new profile |
| `kind` | `LocationKind` | `HOME` |
| `localityId` | int | `localityId` (FK `au_localities`, `ON DELETE RESTRICT`) |
| `latitude`, `longitude` | float | the locality's centroid |
| `point` | geography | **generated** by Postgres from latitude/longitude (never written) |
| `travelRadiusKm` | int | 50 (default radius, decided 2026-09-25) |
| `precision` | `LocationPrecision` | `LOCALITY` (no geocoding at sign-up) |
| `source` | `LocationSource` | `REGISTRATION` |

Hand-written constraints: one `HOME` row per worker (`worker_locations_one_home_per_worker`, partial
unique index); `travelRadiusKm` between 1 and 500 and only on `HOME`; latitude/longitude range checks.

### 2.5 `worker_onboarding` — the onboarding marker

| Column | Type | Value |
|---|---|---|
| `workerProfileId` | text, PK | the new profile |
| `stage` | `OnboardingStage` | `SIGNED_UP` |
| `stageEnteredAt`, `signedUpAt`, `lastActivityAt` | timestamp | now |
| `firstSignInAt`, `firstDocumentAt`, `documentsSubmittedAt`, `verifiedAt`, `publishedAt` | timestamp | NULL |
| `mandatoryTotal`, `mandatoryUploaded`, `mandatoryApproved` | int | 0 |
| `catalogueVersion` | int | 0 |
| `version` | int | 0 (optimistic lock) |

The stage is **derived**, never set by a client ([04 §4](04-enums.md#4-onboardingstage--worker_onboardingstage-worker_onboarding_transitionsfromstagetostage)). At sign-up no
document obligations are known yet, so it is `SIGNED_UP` with zero counts; the onboarding reconciler
fills the counts from `verification_requirements` later.

### 2.6 `worker_onboarding_transitions` — stage history (append-only)

| Column | Type | Value |
|---|---|---|
| `id` | bigint | auto |
| `workerProfileId` | text | the new profile |
| `fromStage` | `OnboardingStage` | NULL |
| `toStage` | `OnboardingStage` | `SIGNED_UP` |
| `at` | timestamp | now |
| `cause` | text | `WorkerRegistered` |
| `actorId` | text | NULL |
| `source` | `OnboardingTransitionSource` | `API` |

### 2.7 `audit_logs`

| Column | Type | Value |
|---|---|---|
| `id` | text (cuid) | generated |
| `userId` | text | the new user |
| `action` | `AuditAction` | `ACCOUNT_REGISTERED` |
| `metadata` | json | `{ "workerProfileId": "…", "breachedPasswordCheck": "clear" \| "unknown" }` (a breached password never gets this far) |
| `ipAddress` | text | the caller's IP (behind Cloud Run's proxy, from `X-Forwarded-For`) |
| `userAgent` | text | the browser's user agent, first 500 characters |
| `createdAt` | timestamp | now |

### 2.8 `registration_photo_uploads`

Inserted by the photo confirm (4.6b) — or by the multipart upload (4.6c), which nothing calls since the wizard switch —
and claimed by the submit (4.7). No column was added for the direct upload (U3): a row exists only once
the object was checked; which store holds the object is the key's prefix.

| Column | Type | At confirm (4.6b) / upload (4.6c) | At submit |
|---|---|---|---|
| `id` | uuid | the ticket's id (4.6b) or generated (4.6c); returned as `photoUploadId` | — |
| `blobKey` | text, unique | `staging/<id>` (bucket) or `workers/registration/<id>.<ext>` (Blob) | — |
| `url` | text | bucket rows: the staging URL (private; diagnostic only). Blob rows: the public Blob URL, copied to `worker_profiles.photos` on claim | — |
| `contentType` | text | detected from the bytes | — |
| `sizeBytes` | int (> 0) | the object's size | — |
| `ipHash` | text | HMAC of the confirming / uploading IP (never the raw IP) | — |
| `createdAt` | timestamp | now | — |
| `claimedAt` | timestamp | NULL | now |
| `claimedByWorkerProfileId` | text (FK, `SET NULL`) | NULL | the new profile |

Claimable once and only within 24 h of `createdAt`. Unclaimed rows (and their objects) are purged daily
from whichever store the key names. For bucket rows the profile's `photos` is set later by the
processing job to the Vercel Blob URL of `workers/<profileId>/<id>.jpg` (the thumbnail sits beside it as
`<id>-256.jpg`); nothing about that is recorded on the row — the keys derive from the ids. The bucket
itself holds nothing after processing.

### 2.9 `outbox_events`

| Column | Type | Value |
|---|---|---|
| `id` | uuid | generated |
| `type` | text | `WorkerRegistered` (or `RegistrationAttemptOnExistingAccount` for an existing email) |
| `payload` | json | `{ "userId": "…", "workerProfileId": "…" }` (existing email: `{ "userId": "…" }`) |
| `status` | `OutboxStatus` | `PENDING` |
| `attempts` | int | 0 |
| `nextAttemptAt` | timestamp | now |
| `lockedUntil`, `lastError`, `processedAt` | | NULL |
| `createdAt` | timestamp | now |

What happens next: [05-events-and-emails.md](05-events-and-emails.md).

### 2.10 `rate_limit_buckets` — fixed-window counters

| Column | Type | Value |
|---|---|---|
| `key` | text | the endpoint's rule and the caller: the IP for a per-IP limit, `*` for the global one |
| `windowStart` | timestamp | start of the window |
| `count` | int | requests so far in the window |
| `expiresAt` | timestamp | when the counter can be deleted (purged every 10 minutes) |

## 3. Tables read (not written) by a sign-up

| Table | Read by | What |
|---|---|---|
| `au_localities` | 4.1 suburb search; 4.7 submit | Suburb list (G-NAF): `id`, `suburb`, `searchName`, `state`, `postcode`, `latitude`, `longitude`, `retiredAt`. Search uses an in-memory copy; the submit checks the id exists and `retiredAt IS NULL`. Rows are never deleted, only retired. |
| `"Category"` | 4.2; 4.7 | `id`, `name`, `requiresQualification` |
| `"Subcategory"` | 4.2; 4.7 | `id`, `categoryId`, `name`, `requiresRegistration` |
| `users` | 4.3; 4.7 | Is the email taken? |

## 4. Row relationships

```
users 1 ── 1 worker_profiles 1 ──┬── n worker_services          (categoryId -> "Category".id, by value)
                                 ├── n worker_locations ── n..1 au_localities
                                 ├── 1 worker_onboarding
                                 ├── n worker_onboarding_transitions
                                 └── n registration_photo_uploads (claimedByWorkerProfileId)
users 1 ── n audit_logs
outbox_events: no foreign keys; payload carries userId / workerProfileId
```

Deleting a `worker_profiles` row cascades to its services, locations, onboarding marker and transitions;
staged photos keep their row with `claimedByWorkerProfileId` set to NULL.

## 5. Legacy sign-up (historical)

**Removed on 2026-10-02.** Until then the pre-S1 page posted to apps/app's `POST /api/auth/register-async`
(`lib/workers/workerRegistrationProcessor.ts`, both deleted; last version at git tag-less commit `b7ccc80`).
Kept here because rows written by it still exist in production and differ from the api's (mobile as typed,
no `worker_locations` row until the S1 backfill, `LOGIN_SUCCESS` as the registration audit action).

| Table | What it wrote |
|---|---|
| `users` | `email` (lower-cased), `passwordHash`, `role = WORKER`, `status = ACTIVE` |
| `worker_profiles` | names, `mobile` **as typed** (not E.164), `location` (the string the page built), `photos` (the URL uploaded earlier by `/api/upload/worker-photo`), `city`/`state`/`postalCode`/`latitude`/`longitude` from a **Google geocode** of the location string, `languages = []`, `profileCompleted = false`, `isPublished = false`, `verificationStatus = NOT_STARTED` |
| `worker_services` | one row per category, as in 2.3 (unknown ids skipped silently) |
| `audit_logs` | `action = LOGIN_SUCCESS`, metadata `{ registrationType: WORKER, emailSent: true }` (fire-and-forget) |

Not written by legacy: `worker_locations`, `worker_onboarding`, transitions, `registration_photo_uploads`,
`outbox_events`, the three S1 columns. It also posts to the n8n webhook (CRM) directly, not through an
outbox. No email verification, no breach check, no transaction across the inserts.
