# `@remonta/infra` — apps/api on Google Cloud Run

How the api runs, as code, without an infrastructure tool to learn:

| Piece | File | Role |
|---|---|---|
| The stage table | `lib/stages.ts` | **The single source of truth**: two services, `remonta-api-staging` and `remonta-api`, in `australia-southeast1`; instances, CPU/memory, the plain environment, the eight secret names (the api token pair included) |
| Rendered service definitions | `cloudrun/service.staging.yaml`, `cloudrun/service.prod.yaml` | What Cloud Run runs (Knative `Service`), generated by `pnpm run render`; a drift test fails if they differ from the table |
| One-time project setup | `cloudrun/bootstrap.sh` | Idempotent `gcloud`: APIs, Artifact Registry, service accounts, empty secrets, Workload Identity Federation for GitHub, log metrics, retention, alert channel + policies (through `apply-alerts.sh`). Shares its stage table with `apply-alerts.sh` via `cloudrun/lib.sh` |
| Photo buckets | `cloudrun/storage/lifecycle.json`, `cors.<stage>.json`; bootstrap step 11 | One regional, **private, upload-only** bucket per stage (`remonta-api-photos[-staging]`, named in the stage table and in `lib.sh`): uniform access, public access prevention enforced, soft delete 7 days, `staging/` objects deleted after a day, CORS for the stage's app origins and `POST`, the runtime account as object user and as its own token creator (policies are signed through IAM, no key file), Cloud Storage write audit logs, two log metrics. The clean copies live in Vercel Blob (the organisation's domain-restricted sharing forbids public grants, 2026-10-05) |
| Apply alert policies | `cloudrun/apply-alerts.sh <stage>` | `cloudrun/monitoring/*.json` is the source of truth: the script creates a missing policy, updates one whose live definition differs, leaves the rest (`created` / `updated` / `unchanged`); `--dry-run` only reads and prints the differences; `--only <policy>` for one. Run it after merging a policy edit; `test/monitoring.test.ts` pins the files' shape |
| Deploy | `.github/workflows/deploy-api.yml`, `.github/scripts/api-health.sh` | Push to `main` → build `api:<sha>` → **staging**. Production is a `workflow_dispatch` promotion of an image already on staging |

## The api token secret (U1 api-identity, 2026-10-08)

`apps/app` mints a 5-minute JWT from the admin's session and `apps/api` verifies it (`docs/admin/README.md`). Both
sides hold the same HS256 secret **per stage**; the pairing rule is **Vercel Preview <-> staging, Production <->
prod**. The api has two secrets: `<service>-API_TOKEN_SECRET` (current) and `<service>-API_TOKEN_SECRET_PREVIOUS`
(the old value during a rotation; a throwaway random value otherwise, seeded by bootstrap step 4b). Both are always
mounted, so a rotation never touches the stage table or the YAML. The api refuses to boot without the current one.

**Set it (once per stage, before the first promotion that needs it):**

```bash
openssl rand -base64 32 | gcloud secrets versions add remonta-api-staging-API_TOKEN_SECRET --data-file=-   # staging
openssl rand -base64 32 | gcloud secrets versions add remonta-api-API_TOKEN_SECRET --data-file=-           # prod (a different value)
```

Then in Vercel, project `remonta-app`, variable `API_TOKEN_SECRET`: the staging value in the **Preview** scope, the
prod value in the **Production** scope. Redeploy the api (a `deploy-api` dispatch of the running sha is a new
revision that re-reads `latest`) and the app.

**Rotate it (no downtime; the previous value is accepted for the window):**

1. `NEW=$(openssl rand -base64 32)`; `OLD` = the current value. Api: `printf '%s' "$OLD" | gcloud secrets versions
   add <service>-API_TOKEN_SECRET_PREVIOUS --data-file=-`, then `printf '%s' "$NEW" | gcloud secrets versions add
   <service>-API_TOKEN_SECRET --data-file=-`; redeploy the service. Tokens signed with either verify.
2. App: set `API_TOKEN_SECRET` = `NEW` in the matching Vercel scope; redeploy the app. New tokens use `NEW`.
3. After at least 5 minutes: `openssl rand -base64 32 | gcloud secrets versions add
   <service>-API_TOKEN_SECRET_PREVIOUS --data-file=-` (a throwaway again); redeploy the api. Disable the older
   versions of both secrets; destroy them after a week.
4. Check: no `auth-failed` email during the window; `gcloud secrets versions list` shows one enabled version each.

Staging and prod rotate independently. A mismatch between a Vercel scope and its api shows within minutes as
`bad-signature` rejections (`jsonPayload.auth="rejected" AND jsonPayload.reason="bad-signature"`) and, on prod, the
`auth-failed` alert (`cloudrun/monitoring/auth-failed.json`).

## Why Cloud Run, and how it is configured

The api runs an outbox dispatcher and a scheduler between requests, so it needs a process that is always
on. Cloud Run gives that with **instance-based billing** (`run.googleapis.com/cpu-throttling: 'false'`) and
**minimum one instance**. Everything else is Cloud Run's default: TLS at the `run.app` URL, regional
redundancy, autoscaling (prod up to 4), logs in Cloud Logging (the api's JSON lines land as `jsonPayload`),
metrics in Cloud Monitoring. Cloud Run terminates TLS and adds `X-Forwarded-Proto`/`X-Forwarded-For`, so the
api runs with `TRUST_PROXY=1`. Its startup and liveness probes hit `/v1/health`, the contract's `probe`
entry (served over plain HTTP, never load-shed).

**No custom hostname for now (D16):** Cloud Run domain mapping is not offered in Sydney, and the alternatives
add a load balancer. The api's URL is `https://remonta-api[-staging]-<project number>.australia-southeast1.run.app`
and only the app's JavaScript calls it (`NEXT_PUBLIC_API_URL`). **No WAF (D20):** the api's own limits stand.

## Bootstrap (the user, once, ~15 min)

```bash
gcloud auth login                                   # an Owner of the (new) project, billing attached
./infra/cloudrun/bootstrap.sh <project-id>          # prints the three GitHub repository variables
```

Set in GitHub → Settings → Secrets and variables → Actions → **Variables**: `GCP_PROJECT_ID`,
`GCP_WORKLOAD_IDENTITY_PROVIDER`, `GCP_DEPLOY_SERVICE_ACCOUNT` (from the script's output). Then add the six
secret **values** for the stage about to deploy:

```bash
printf '%s' '<value>' | gcloud secrets versions add remonta-api-staging-AUTH_DATABASE_URL --data-file=-
# … RECAPTCHA_SECRET_KEY, RESEND_API_KEY, IP_HASH_SECRET (openssl rand -hex 32), BLOB_READ_WRITE_TOKEN, N8N_REGISTRATION_WEBHOOK_URL
```

Staging's `AUTH_DATABASE_URL` is the `rehearse-w1` Neon branch's **pooled** string; its reCAPTCHA secret is
the staging key pair (domain `vercel.app`). A service whose secret is missing does not start; Cloud Run keeps
the previous revision and the deploy job fails — by design.

## Deploying

- **Staging deploys itself** on a merge to `main` touching `apps/api/**`, `packages/**`, `infra/**` or the
  lockfile. The job prints the service URL; `NEXT_PUBLIC_API_URL` in Vercel's Preview scope points at it.
- **Production is a promotion:** Actions → deploy-api → Run workflow → `stage=prod`, `imageTag=<the sha that
  passed the preview checklist>`. Nothing deploys to production on a push.
- **Rollback**, either stage: the same dispatch with a previous SHA (images stay in the registry: newest 20),
  or Cloud Run → service → Revisions → route traffic to the previous revision.
- **Pause staging** between test rounds to save its always-on cost:
  `gcloud run services update remonta-api-staging --region australia-southeast1 --min-instances=0 --cpu-throttling`
  (the next deploy restores the table's settings).

## Cost (Sydney, instance-based billing, approximate)

One always-on 1 vCPU / 512 MiB instance ≈ A$80–100 a month; prod at 1 GiB slightly more; a second
environment doubles it. Requests, registry storage and logs at this traffic are a few dollars.
